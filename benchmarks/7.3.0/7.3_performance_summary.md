# IAM 7.3.0 Performance Test Results

During each release, we execute various automated performance test scenarios and publish the results.
This document will be helpful for capacity planning as it reflects realistic user scenarios.

The results cover **five node configurations** — Two Node 2 Core, Single Node 4 Core, Two Node 4 Core, Three Node 4 Core, and Four Node 4 Core. The four 4 Core configurations use `c6i.xlarge` EC2 instances. The Two Node 2 Core cluster runs 2 vCPU nodes and was measured over the **50 – 500 concurrency range only**, so it reads `-` above 500 concurrent users in the tables below and appears on the 50 – 500 charts only.

| Test Scenario | Description |
|---|---|
| OIDC Auth Code Grant Redirect With Consent | Obtain an access token and an id token using the OAuth 2.0 authorization code grant type. |
| OIDC Auth Code Grant Redirect Without Consent | Obtain an access token and an id token using the OAuth 2.0 authorization code grant type without consent. |
| OIDC Auth Code Grant Redirect Without Consent Retrieving User Attributes | Obtain an access token and an id token using the OAuth 2.0 authorization code grant type without consent. Retrieve country, email, first name and last name as user attributes. |
| OIDC Auth Code Grant Redirect Without Consent Retrieving User Attributes, Groups and Roles | Obtain an access token and an id token using the OAuth 2.0 authorization code grant type without consent. Retrieve country, email, first name and last name as user attributes. Additionally retrieve groups and roles as well. |
| SAML2 SSO Redirect Binding | Obtain a SAML 2 assertion response using redirect binding. |
| App Native Authentication | Obtain an access token and an id token using the app native authentication flow. |
| Token Exchange Grant Type | Obtain an access token and an id token using the token exchange grant type. |
| Client Credentials Grant Type | Obtain an access token using the OAuth 2.0 client credentials grant type. |
| OIDC Password Grant Type | Obtain an access token and an id token using the OAuth 2.0 password grant type. |

Our test client is [Apache JMeter](https://jmeter.apache.org/index.html). We test each scenario for a fixed duration of
time and split the test results into warm-up and measurement parts and use the measurement part to compute the
performance metrics. For this particular instance, the duration of each test is **15 minutes** and the warm-up period is **5 minutes**.

We run the performance tests under different numbers of concurrent users to gain a better understanding of how the server reacts to different loads.

## Understanding the Metrics

### Throughput

Throughput reflects the number of operations processed per second by the cluster. For multi-step authentication flows (e.g., Authorization Code Grant), this measures how many **complete end-to-end flows** are completed per second, not individual HTTP requests. Because every step of a flow executes once per iteration, this rate is effectively that of the **primary bottleneck step** that gates the flow. For single-step machine-to-machine grants, it is the number of **requests per second** at the `/token` endpoint. Throughput is the primary indicator of horizontal scalability across node configurations.

### Response Time

Multi-step authentication flows involve several sequential HTTP requests. For these flows, the response time reported is the **95th percentile of the primary bottleneck step** — the step with the highest response time under load, marked with **✦** in the per-scenario step tables below. The throughput reported for the same scenario corresponds to this bottleneck step, so both metrics describe the same gating step of the flow. For single-step grants, both the response time and throughput are those of the single `/token` request.

> Response times shown are **95th percentile values in milliseconds**.

> **Reading the charts:** the 50 – 500 charts carry all five configurations. Where they differ by more than 8× *at the same concurrency*, the chart is drawn on a **log y-axis** — otherwise the four 4 Core series collapse into one flat band against a single 2 Core spike; the axis label says so on those charts. The 50 – 3000 charts cover the four 4 Core configurations only and are linear throughout, unchanged from the previous publication.
